# SchemaSeed Workbench i18n

> Status: implemented for the production Generation Workbench UI (`ui/generation-workbench/app.mjs`) and its presentation layer (`src/i18n/**`).
>
> 本文档说明界面语言（UI language）的解析与 fallback、它与 synthetic data locale 的分离、message key 契约、diagnostics 本地化与渐进披露设计。它不改变 Generation Core 算法、generator 选择逻辑、blocking 语义或 DBX Host 协议。

## 两个必须分开的 locale

| 概念 | 属性 | 取值 | 影响 | 存储 |
| --- | --- | --- | --- | --- |
| UI language（界面语言） | 纯 presentation | `zh-CN` / `en-US` | 界面文字、diagnostics 文案、mapping 状态词 | `localStorage["schemaseed.workbench.uiLocale"]` |
| Synthetic data locale（数据语言） | Generation Core 输入 | `zh-CN` / `en` | deterministic 生成值的语言形态（测试姓名 / 地址 / 手机号标记等） | Workbench session controls（`GenerationPlan.locale`） |

这两个值永远不会互相推导：

- 切换界面语言只重新渲染文案：不调用 Core、不重建 GenerationPlan、不改变 dataset、不改变 blocking 状态；
- 切换数据语言只影响生成结果：不会改变界面语言；
- Workbench 在使用 `GenerationPlan.locale` 的地方（例如 Preview summary）以「数据语言」标注该值，避免用户把它误读成界面语言。

回归测试：`tests/i18n.test.mjs` 的 “UI locale and synthetic data locale stay independent”。

## Locale 解析顺序

```text
DBX Host locale（仅当 Host 真正暴露时）
  → 用户已保存的 SchemaSeed UI locale
    → browser locale（navigator.language）
      → en-US（默认 fallback）
```

`src/i18n/ui-locale.mjs` 实现该顺序：

- `readHostLocale(host)`：DBX Host API `^1.3` 不暴露 locale（`capabilities`、`context`、`invoke`、`onContext`、`getTableMetadata` 均无该字段），因此该级通常为空。SchemaSeed 不臆造 Host locale；只有当 Host 真的返回非空 `locale` / `uiLocale` / `language` 字符串时才使用它。
- `readSavedLocale(storage)`：读取用户上次选择的界面语言；`localStorage` 不可用或抛错时静默回退。
- `resolveUiLocale({ hostLocale, savedLocale, navigatorLanguage })`：返回 `{ locale, source }`，`source` 取值 `host` / `saved` / `browser` / `default`。
- `normalizeUiLocale(value)`：`zh`、`zh-CN`、`zh-SG`、`zh-Hans-CN`、`zh_CN` 等映射到 `zh-CN`；`en`、`en-US`、`en-GB` 映射到 `en-US`；其他语言返回 `null`，由上层继续 fallback。

## Message key 契约

- 目录：`src/i18n/en-US.mjs`、`src/i18n/zh-CN.mjs`，key 为扁平 dotted key（`context.title`、`actions.generate`、`diagnostic.<code>.title`）。
- `en-US` 是 reference locale：任何 key 缺失都回退到 `en-US`；连 `en-US` 也没有时返回 key 文本本身，从不抛出，也不会让页面 crash。
- `createI18n(locale)` 返回可直接调用的 translator：`t("context.title")`，并附带 `t.locale`、`t.has(key)`、`t.keys()`。
- 插值使用 `{name}`，缺失的插值参数保留原占位符（便于发现遗漏），不会产生 `undefined`。
- 测试保证 key parity 双向一致：`missingMessageKeys("zh-CN")` 必须为空，zh-CN 不允许存在 en-US 没有的 key（`tests/i18n.test.mjs`）。
- 不得在组件中写 `locale === "zh-CN" ? "生成" : "Generate"`；UI 源码中有测试防止 inline locale 分支与硬编码中文。
- UI 静态文案通过 `data-i18n="key"` 绑定，动态文案通过 `src/i18n/workbench-messages.mjs` 的纯函数生成（可在无 DOM 环境下测试）。

不翻译的内容：database / schema / table / column 名、SQL、DB type、raw schema type、diagnostic `code`、内部 ID、rule identity、evidence source / observation、`GenerationPlan` 中的 `seed` / `locale` 值。

## Diagnostics 契约

数据层与展示层严格分离：

```text
Generation Core / Provider  →  machine-readable diagnostic
{ code, severity, blocking, table, column, rule, reason }

Workbench UI                →  localized human-readable presentation
{ levelLabel, title, description, action, headline, technical }
```

- Core 不拼装中文（或任何最终用户文案），只保证 `code` / `severity` / `blocking` / `reason` 稳定。
- `describeDiagnostic(diagnostic, t)` 按 `diagnostic.code` 映射 `diagnostic.<code>.title` / `.description` / `.action`；可选 `.level` 覆盖标题级别词（例如 `semantic_confirmation_required` 展示为“需要确认”而不是“警告”），但 `severity`、`blocking` 的 machine 值原样保留。
- 未知 code 有安全 fallback：显示“未分类诊断（<code>）”并原样给出 Core `reason`，绝不编造含义。
- `diagnosticTechnicalRows()` 提供折叠区内容：diagnostic code、machine severity、blocking、table / column / rule、Core 原始消息。
- 渐进披露：默认只显示「级别 + 标题」「简短原因」「处理建议」；技术细节位于 `<details>查看技术详情`。

Workbench 的三个高级区域（字段与生成策略 / 生成约束 / 问题诊断）同样使用渐进披露：默认折叠，标题行保留本地化摘要（字段数 / 待确认数 / 约束数 / 诊断级别），普通 warning 不会自动展开「问题诊断」，只有新出现的 blocking error 会自动展开。摘要与展开策略由 `src/workbench/workbench-sections.mjs` 从 view model 派生，可在无 DOM 环境下测试。

示例（zh-CN）：

```text
阻塞：无法确认文本字段的最大长度
DBX 没有返回「category」字段的长度信息，SchemaSeed 无法确认生成值是否超出字段容量，因此不会猜测一个最大长度。
处理建议：请手动指定允许的最大长度，或在 DBX 返回完整字段元数据后重新读取。
查看技术详情 ▸ Diagnostic code / Severity / Blocking / Table / Column / Rule / Raw Core message
```

## 内部 enum 的 presentation 映射

`src/i18n/labels.mjs` 把 Core 的 machine 值映射为本地化标签，内部 enum / protocol / persisted value 一律不变：

- mapping 状态：`Fallback` → 「默认策略」、`Needs confirmation · fallback active` → 「待确认 · 当前使用默认策略」、`Ambiguous` / `Incompatible` 等同理；`toColumnViewModel()` 额外暴露稳定 token `mappingStatusToken` 供 UI / 测试使用。
- confidence、semantic type、generation rule 名称与 Rule Editor 字段标签、constraint kind、constraint plan（可满足 / 容量 / 阻塞）均由 catalog 提供；未知值回退到 Core 提供的 label 或原始标识符。

## 测试与维护

```bash
node --test tests/i18n.test.mjs tests/diagnostics-localization.test.mjs
```

覆盖内容：

- locale 解析与 fallback（host / saved / browser / default、`zh` 区域变体、未支持语言）；
- 缺失 key、未知 key、未知 diagnostic code 均不 crash；
- UI locale 与 synthetic data locale 互不影响（双向回归）；
- `varchar_length_unknown` 与 `semantic_confirmation_required` 的 zh / en 文案、machine 字段保持、technical detail 可达；
- blocking / Export 禁用等安全语义在两种界面语言下完全一致；
- 静态扫描 `src/**` 中所有 diagnostic code，断言两种语言都有 `title` 与 `description`（新增 code 忘记翻译会直接测试失败）；
- 扫描 UI 源码中引用的 message key，断言 key 真实存在；并断言 Generation Core 发布的每个 rule kind / editor field 都有本地化标签。

新增语言的步骤：复制 `en-US.mjs` 为 `<locale>.mjs`，翻译文案（含 `diagnostic.*`），在 `src/i18n/catalog.mjs` 注册，在 `src/i18n/index.mjs` 的 `SUPPORTED_UI_LOCALES` / `LOCALE_BY_LANGUAGE` 中登记，并在 `ui/generation-workbench/app.mjs` 的语言下拉中获得 `uiLocale.<locale>` 标签。key parity 测试会指出所有遗漏。
